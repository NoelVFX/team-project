# Team Contract

## Purpose of this Contract

This contract defines how our team will collaborate on the University Learning Progress Tracker. Our goal is to deliver a reliable, well-tested Java Swing application while maintaining a respectful, inclusive, and accountable working environment.

The contract applies to our communication, planning, implementation, code review, testing, and pull requests. We may revise it when all team members agree to the change.

---

## Team Norms and Expectations

### Communication

- We will use the team's shared group chat for day-to-day communication and GitHub issues and pull requests for project decisions, technical discussion, and review history.
- Each teammate will respond to a message within 24 hours on weekdays and within 48 hours on weekends, even if the response is only to acknowledge the message and provide an update.
- We will notify the team as soon as possible if we cannot attend a meeting, complete an assigned task, or meet an agreed deadline.
- We will raise blockers early instead of waiting until the deadline. A blocker should include what was attempted, the error or issue encountered, and what help is needed.
- We will keep task status visible to the team and update the relevant GitHub issue or project board when work starts, is blocked, or is completed.
- Communication will be respectful and inclusive. We will listen actively, avoid interrupting, explain technical decisions clearly, and give every teammate a meaningful opportunity to contribute.
- Feedback will focus on the code, decision, or process rather than the person. We will ask questions before making assumptions about someone's intent.

### Meetings and planning

- We will attend scheduled team meetings prepared, having reviewed assigned tasks and any relevant pull requests beforehand.
- At the beginning of a work session, we will confirm priorities, owners, and acceptance criteria. At the end, we will record decisions, remaining work, and blockers.
- We will divide work according to the agreed use-case ownership while helping one another when a task is blocked or a deadline is at risk.
- We will avoid making large changes outside the agreed scope of a task without discussing them with the team first.

### Code and repository practices

- Each feature will be developed on its own branch. We will not commit directly to the main branch.
- Each pull request will describe the change, identify the relevant use case, and include the tests or verification performed.
- Pull requests should be small enough to review and should avoid unrelated formatting changes or drive-by refactors.
- At least one other teammate will review each pull request before it is merged. The author is responsible for responding to review comments and confirming that requested changes are addressed.
- We will run the relevant tests before opening or updating a pull request. A pull request should not be merged while known tests are failing unless the team has explicitly discussed and documented the reason.
- We will preserve the project's Clean Architecture boundaries: entities contain business rules, use cases orchestrate, interface adapters translate data, and views do not depend directly on entities.
- We will not commit passwords, API keys, tokens, private credentials, or other secrets to the repository.
- Before merging, the author and reviewer will check for accidental changes to unrelated files and confirm that the branch is based on the current target branch when appropriate.

### Contribution and ownership

- Each teammate is responsible for completing their assigned use cases, tests, documentation, and integration work to the agreed standard.
- Ownership does not prevent collaboration. Team members may pair program, review code, or help debug another member's work when needed.
- We will credit contributions accurately and communicate before taking over another teammate's task.
- If a task is larger than expected, we will split it into smaller tasks or renegotiate its scope rather than silently leaving it incomplete.
- We will share enough context in commits, issues, and pull requests that another teammate can understand and maintain the work.

---

## Decision Making

- We will seek consensus for architecture, shared entities, data-access interfaces, public APIs, and changes that affect more than one use case.
- For routine implementation choices within an assigned use case, the owner may make the decision after considering existing project conventions and review feedback.
- If consensus cannot be reached, each teammate will have one vote and the majority decision will be used. The decision and its rationale will be recorded in the relevant GitHub issue or pull request.
- Decisions that affect the whole application should not be finalized in a private conversation without informing the rest of the team.

---

## Conflict Resolution

1. The people involved will discuss the issue directly and respectfully, using specific examples and focusing on the project or process rather than personal criticism.
2. Each person will explain their perspective and confirm that they understand the other person's concerns before proposing a solution.
3. The team will consider alternatives and aim for a compromise that supports the project requirements and agreed architecture.
4. If the conflict remains unresolved, the full team will review the issue and make a decision using the decision-making process above.
5. If the team still cannot resolve the issue, we will ask the TA or instructor for guidance as a team.

A disagreement about code is not a reason to delay communication, withhold review, or make unannounced changes to another teammate's work.

---

## Accountability

Each team member agrees to:

- complete their assigned work by the agreed deadline;
- communicate progress and blockers honestly and early;
- attend meetings or notify the team when attendance is not possible;
- write and maintain tests for the behaviour they implement;
- review teammates' pull requests carefully and promptly;
- follow the repository, branching, and security practices in this contract;
- ask teammates, TAs, or instructors for help when necessary;
- keep documentation, issue status, and acceptance criteria up to date; and
- take responsibility for correcting mistakes rather than hiding them.

If a teammate repeatedly misses commitments without communication, the team will first discuss the issue privately and agree on a recovery plan. If the issue continues, we will document the missed commitments and consult the TA or instructor.
